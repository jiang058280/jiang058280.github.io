把角色命名为“专家”不会自动提升准确率。多 Agent 的价值通常来自上下文隔离、工具权限隔离或独立子任务并行；它也引入额外延迟、通信成本和结果冲突。应先明确单 Agent 的瓶颈。

## 用任务依赖决定并发

以经营分析为例，指标定义和数据查询存在先后关系，报告需要等待查询和分析完成。如果多个产品的独立查询可以分别进行，则适合并发。不能把所有步骤同时启动，再让报告 Agent 猜测尚未返回的数据。

子任务至少包含 task_id、输入、期望输出结构、截止时间和错误策略。结果合并按 ID 和类型处理，不能仅把几段自然语言拼接后要求另一个模型“自行判断”。数值对比应使用可复查的计算逻辑。

## 局部失败与全局结论

某个渠道查询失败时，系统可以给出已完成部分，但必须标明缺失范围。不能把部分数据写成全渠道结论。是否重试、降级或终止，应按任务对完整性的要求决定。

## 比较收益而不是只看演示

在同一任务集上比较单 Agent 和多 Agent 的成功率、总 token、P95 延迟及错误恢复。若只是把一段提示词拆成三次调用，却没有质量收益，就没有必要增加部署单元。

协作协议解决消息交换问题，任务规划和业务正确性仍属于应用。架构图中应标出谁负责权限、谁决定完成、谁汇总错误，这比角色数量更重要。
