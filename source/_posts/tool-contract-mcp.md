工具描述决定模型如何理解能力，执行契约决定系统如何安全运行。一个名称含糊、参数全部是字符串的工具，很难稳定处理复杂业务。应先设计业务接口，再决定怎样暴露给模型。

## 参数与结果都需要约束

查询订单工具可以明确 start_time、end_time、timezone 和 tenant_id 的来源。租户身份应由服务端注入，不能由模型任意指定。输出包含 status、rows、truncated 和 error_code，避免把“无结果”和“调用失败”都返回空列表。

```json
{"status":"ok","rows":[],"truncated":false}
```

这只是返回结构示例。它表达查询成功但没有行，与超时错误的业务含义不同。模型可据此向用户说明无数据，而不是声称数据库不可用。

## MCP 所处的位置

MCP 定义应用与外部服务交换工具和上下文的协议。它让连接方式更统一，但不会自动提供业务正确性，也不负责替代应用的任务调度。具体功能和鉴权方式应按采用的协议及 SDK 版本核对。

## 把副作用关在可审计边界内

读取、导出和写入应使用不同能力范围。发送消息、修改订单等操作需要明确授权与幂等机制。即使使用标准协议，也要校验真实用户权限、限制返回数据量，并处理敏感字段。

工具验收应包括类型错误、缺参、越权、超时、重复调用和空结果。协议兼容只是第一步，模型能否正确选择工具以及程序能否执行约束仍需独立验证。
